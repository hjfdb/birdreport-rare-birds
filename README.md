# 观鸟地区稀有鸟种榜

基于 **中国观鸟记录中心**（[birdreport.cn](https://www.birdreport.cn/)）公开数据的「按行政区汇总本地稀有鸟种」服务，包含一个 **Node.js 服务端** 和一个 **网页端**。

选定 省 / 市 / 区县 与起止日期后（默认 **当天**），页面会把该区域**记录数最少的鸟种排在最前面**——记录越少，说明这种鸟在本地越稀有；同时标注每种鸟的保护等级（《国家重点保护野生动物名录》国家一级 / 国家二级 / 三有名录）、IUCN 红色名录等级、是否中国特有。

**榜单的两个口径是分开的**（这是本项目最关键的设计）：

| | 数据源 | 作用 |
| --- | --- | --- |
| **成员**：这段时间里出现过哪些鸟 | `record/activity/taxon` **带**起止日期 | 榜单显示哪些卡片 |
| **稀有度**：谁更稀有 | `record/activity/taxon` **最近两年**（去年 1 月 1 日起至今） | 榜单的排序与稀有度条 |

为什么必须分开：时间窗口一窄（例如「当天」），几乎所有鸟种都只有 1 条记录，排序就完全没有信息量；
换用宽口径后，「这种鸟在北京**最近两年**总共只被记录过 1 次」才是真正的稀有信号。

为什么宽口径用「最近两年」而不是全时段：全时段在大地区上是很重的聚合（北京经常 20 秒以上、
还时不时 500），两年窗口既有足够的统计量、上游也更扛得住；口径固定（锚在去年 1 月 1 日）
配合**一个月的缓存**，一个地区一年里基本只回源十几次。实测（2026-10，北京市）两年窗口返回
570 个鸟种、约 16 秒；常见鸟的两年记录数约为全时段的六成（灰喜鹊 39051 vs 65708），口径内部一致。
两个口径各存一份缓存，互不影响。

## 快速开始

### 方式一：下载现成的可执行文件（不用装 Node）

到 **[Releases](../../releases/latest)** 按自己的系统选一个：

| 系统 | 下载 | 怎么用 |
| --- | --- | --- |
| Windows | `birdreport-rare-birds-vX.Y.Z-win-x64.zip` | 解压后双击 `观鸟地区稀有榜-vX.Y.Z-win-x64.exe` |
| macOS · Apple 芯片 | `birdreport-rare-birds-vX.Y.Z-mac-arm64.zip` | 解压，见下方命令 |
| macOS · Intel 芯片 | `birdreport-rare-birds-vX.Y.Z-mac-x64.zip` | 解压，见下方命令 |
| Android（64 位手机） | `birdreport-rare-birds-vX.Y.Z-android-arm64.apk` | 直接装，见下方说明 |

不确定自己是哪种 Mac：**  → 「关于本机」，芯片写「Apple M…」选 arm64，写「Intel」选 x64。

macOS 上的程序没有图形界面，在「终端」里运行（把路径换成你解压出来的那个文件）：

```bash
cd ~/Downloads
./观鸟地区稀有榜-vX.Y.Z-mac-arm64
```

启动后浏览器会自动打开 <http://127.0.0.1:8787/>；Windows 上关掉那个黑色控制台窗口、
macOS 上按 <kbd>Ctrl</kbd>+<kbd>C</kbd> 即停止服务。缓存落在程序同级的 `data/` 目录
（该位置不可写时退到用户数据目录）。

> **两个平台都会提示「未签名」** —— 程序由 Node 官方 SEA 机制注入生成，注入会让原签名失效，
> 自己签证书需要额外成本：
>
> - **Windows**：SmartScreen 提示「未知发布者」，点「更多信息 → 仍要运行」即可。
> - **macOS**：Gatekeeper 会**直接拦住**（「无法打开，因为 Apple 无法检查其是否包含恶意软件」），
>   且**没有「仍要运行」按钮**。办法：在 Finder 里**右键点该文件 → 打开 → 再点「打开」**，
>   或到 系统设置 → 隐私与安全性 底部点「仍要打开」。只需绕过一次。
>   命令行里也可一次性解除：`xattr -d com.apple.quarantine 文件名`
>
> 介意的话可以按方式三自己构建。

**Android** —— 把 APK 传进手机点开安装即可（首次需允许「安装未知来源应用」）：

```bash
# 或者用数据线装（需要 adb 在 PATH 里）
adb install -r birdreport-rare-birds-vX.Y.Z-android-arm64.apk
```

APK 里**内嵌了一整个 Node 运行时**（nodejs-mobile 的 `libnode.so`，内核 Node 18.20.4）和
整套服务端 + 网页代码，装上就是自包含的，**不需要额外装任何东西**。首次启动会先把运行时解包到
应用私有目录（大约 1~3 秒，界面上有进度圈），然后用 WebView 打开 `http://127.0.0.1:8787/`。

几点要知道的：

- **只支持 64 位 ARM 手机**（`arm64-v8a`），2020 年后的机器基本都是；APK 约 48 MB，其中 47 MB 是 Node 运行时。
- **需要 Android 7.0（API 24）及以上**。Android 9 起默认禁止明文 HTTP，这里已用
  `network_security_config.xml` **只对 `127.0.0.1` / `localhost`** 开了一个口子，其它域名仍然禁止。
- **App 本身要联网** —— 数据实时取自 birdreport.cn，它只是把服务端搬进了手机。
- **缓存**落在应用私有目录，卸载才清掉。
- 看日志：`adb logcat -s BirdNode`（Node 的 stdout / stderr 都转到 logcat 了）。
- 退出 App 会**直接结束进程** —— 不然下次打开时 8787 端口还被上一次占着。

### 方式四：自己构建 Android APK

```bash
npm run build:apk          # 产物在 dist/birdreport-rare-birds-v<版本>-android-arm64.apk
npm run build:apk -- --debug   # debug 版（构建快，但体积大、启动慢）
```

一条命令搞定：脚本会自己找 JDK 17（找不到会明确告诉你去装，而不是丢一堆编译错误）、
缺 nodejs-mobile 运行时（约 130 MB）就自动下载、缺 `android/local.properties` 就按
`ANDROID_SDK_ROOT` 补上。

**前置条件**（一次性准备）：

| 需要 | 版本 | 说明 |
| --- | --- | --- |
| JDK | **17+** | AGP 8.x 的硬要求。机器上 `JAVA_HOME` 指着 JDK 8 也没关系，脚本会另找 |
| Android SDK | platforms **33**、build-tools **33.0.2** | 用 sdkmanager 装 |
| NDK | **25.1.8937393** | 编译 `native-lib.cpp`（拉起 Node 的那几行 C++） |
| CMake | **3.22.1** | 同上 |

```bash
sdkmanager "platforms;android-33" "build-tools;33.0.2" \
           "ndk;25.1.8937393" "cmake;3.22.1"
```

想手动跑 Gradle 也可以（要自己保证 `JAVA_HOME` 是 JDK 17）：

```bash
cd android
./gradlew :app:copyApkToDist      # 打 release 并把产物改名放进 ../dist
```

**关于签名**：签名文件（`android/keystore.properties` 连同 `android/keystore/birdreport.jks`）
**随私有库提交**，本地构建与 CI 共用同一把钥匙 —— 这样 CI 出的 APK 就是正式签名，
手机上不用「先卸载 debug 版再装」。
没有这份文件时构建不会失败，而是**退回 debug 密钥签名** —— 产物照样能装，只是不能上架、
且以后换成正式密钥时必须先卸载再装。要换钥匙就在 `android/keystore.properties` 里写：

```properties
storeFile=keystore/birdreport.jks
storePassword=…
keyAlias=birdreport
keyPassword=…
```

CI 上也可以用 4 个 Secrets（`ANDROID_KEYSTORE_BASE64` / `ANDROID_KEYSTORE_PASSWORD` /
`ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD`）**覆盖**仓库里的钥匙——配了 Secrets 就优先用 Secrets；
都不配就走仓库里的 `android/keystore.properties`（再没有才退回 debug 密钥）。

> ⚠ **上面「随库提交」的前提是仓库为私有**。一旦打算转公开：先从全部分支与历史里移除这两个文件、
> 换一把新钥匙（已装机用户需卸载重装），再公开。

## 功能

**网页端**

- 省 / 市 / 区县 三级联动 + 起始 / 结束日期（默认 **当天**；**没有**「近 7 天 / 近 1 年」这类档位按钮，直接填日期即可）
- **记录检索（顶部查询栏）**：观测地点 / 用户名称 / 鸟种名称三个条件，与省市、时间一起下推到上游，
  概览卡、稀有榜、报告明细会一起收窄（例：北京 · 奥森 · Zacco · 灰喜鹊 的记录）；
  鸟种名称在**郑四名录**里解析，支持中文名 / 学名 / 英文名 / 拼音 / 首字母，命中多个不同鸟种时列出候选让人选，条件同时写入地址栏
- 概览统计卡：鸟种数、目 / 科、观鸟报告数、鸟种记录条数、公开报告（前四张可点击下钻明细）
- 保护等级构成：国家一级 / 国家二级 / 三有 / 中国特有 / IUCN 受威胁(CR/EN/VU)
- **本地稀有鸟种排行**：**每行 5 个卡片、展示该时段全部鸟种**（不按 Top N 截断）。
  卡片上的大数字是**该地区最近两年记录数**（排序依据），下面一行注明本时段记录数；
  底部「稀有度」条同样按历史口径，带目科信息与保护等级徽章。**点卡片可看这种鸟出现在哪些公开报告**
  —— 点击时才向上游查询（不预取），弹层里按「发现点 / 发现人 / 时间」列出，点任一行跳到上游报告详情；
  查询条件自动沿用当前页面的地区与日期，并在打开的瞬间定格，之后改页面不影响它
- **「疑问数据」红色标记**：榜单项与卡片上的鸟名**标红**，表示该时段本地区有记录被上游
  半自动标疑（`outside_type=1`）。卡片上给出「疑问 N 条」，并且把本时段记录数拆成
  **「正常 N 条 · 疑问 M 条」**（两者相加恒等于本时段总数，逐一核对过），
  榜单脚注汇总「标红的 X 种含疑问数据，共 Y 条」。
  上游这个标记取不到时不会让整页失败，只是在脚注提示「疑问数据标记暂时取不到」
- **稀有监听（盯鸟）**：**默认就开着**，一直盯着、条件自动跟随 —— 不用手动开关某个条件。
  在「我的」面板里只有两项可设：**是否监听**（开关）与**稀有数量**（≤3 / 10 / 50 / 100 / 300 条）。
  服务端按页面上当前的地区 / 日期 / 观测地点 / 用户 / 鸟种条件定期回上游取一次，把新出现且
  「该地区**最近两年**记录数 ≤ 数量」的鸟种记下来。
  有新发现时**右下角**冒出提示卡（鸟种名 + 本时段条数 + 近两年条数，点一条直接看它的公开报告），
  浮标上带未读角标；点浮标打开**监听历史记录**弹层（时间倒序，每条都注明当时盯的条件，点条目跳到该鸟种的报告明细）。
  条件一变（换个区县、改个日期）监听条件**自动跟着变**，不用重开；改条件只在服务端**重新划一条起跑线**，
  历史记录与「已提醒」表都保留，不会因为换条件把老鸟重报一遍。
  监听状态存在服务端（`data/watch.json`），刷新页面、换设备打开都还在；关掉监听**不会**清空历史记录。
  **Android 端**另有系统通知：应用退到后台时由原生侧接手轮询，发现新鸟种发通知，点通知直接打开历史记录。
  > ⚠ 数量是**绝对条数**，在大范围下很难命中：实测近两年记录数的下界，北京市 **95** 条、北京朝阳区 **64** 条、全国 **286** 条。
  > 所以默认的 ≤3 条只对区县一级有意义；「我的」面板里会把「本时段最稀有的也有 N 条」摊开显示，
  > 并在这一档一种也命中不了时直接建议改到多少条。
- 筛选：全部 / 仅受保护 / 仅国家重点保护 / 仅中国特有，以及按鸟种名、学名搜索
- 图表：逐月鸟种数、逐月报告数、省内下一级（地市或区县）鸟种数排行（三块默认隐藏，见下）
- 支持 URL 直达：`?province=浙江省&city=杭州市&district=西湖区&start=2026-01-01&end=2026-10-10`
  （`all=1` 表示全部时间）

**REST 接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/provinces` | 省级行政区字典 |
| GET | `/api/cities?provinceCode=` | 地级行政区字典 |
| GET | `/api/districts?cityCode=` | 区县字典 |
| GET | `/api/overview?province=&city=&district=&startTime=&endTime=` | 区域概览统计 |
| GET | `/api/hot?…&filter=all&sort=record&q=` | 本地稀有鸟种排行：成员取当前时段，排序按该地区最近两年记录数（不传 `top` 即返回全部） |
| GET | `/api/taxons?…&sort=record&limit=500` | 完整鸟种明细（成员与榜单一致；每条带 `historyCount`，同样按历史稀有度排序） |
| GET | `/api/records?…&page=1&limit=10` | 公开报告明细（**只取上游一页**，默认每页 10 条、上限 50） |
| GET | `/api/trend?…` | 逐月鸟种数 / 报告数 |
| GET | `/api/province-rank?version=CH4` | 全国各省鸟种数排行 |
| GET | `/api/region-rank?province=&city=&level=city\|district` | 省内下一级地区鸟种数 |
| GET | `/api/taxon-search?q=` | 郑四名录检索（中文名 / 学名 / 英文名 / 拼音 / 首字母） |
| GET | `/api/taxon-resolve?name=` | 鸟种名称 → `taxon_id`（在郑四名录里解析，带候选） |
| GET | `/api/taxon-level?id=` | 单个鸟种的保护等级 |
| GET | `/api/cache` | 缓存策略与命中情况总览 |
| POST | `/api/cache/flush` | 立即把缓存落盘 |
| POST | `/api/cache/clear` | 清空接口结果缓存（保护等级字典不受影响） |
| GET | `/api/protection/status` | 保护等级字典缓存进度 |
| POST | `/api/protection/sync` | 后台预热全部鸟种的保护等级 |
| GET | `/api/health` | 健康检查 |
| GET | `/api/watch` | 稀有监听：当前状态（条件 / 稀有数量 / 基线数 / 历史记录 / 最近检查结果），**不回源** |
| POST | `/api/watch?province=…&startTime=…&endTime=…&label=…&maxHistoryCount=…[&defer=1]` | **只同步条件、不动开关**（页面每次查询后自动跟随条件走的就是这条；`defer=1` 不等基线建完就返回） |
| POST | `/api/watch?enabled=1&…` | 打开监听（或改完数量重开，**重建基线**、历史记录与「已提醒」表保留）；`enabled=0` 关闭（条件留着，下次打开不必重设） |
| GET | `/api/watch/check[?force=1]` | 跑一轮检查，返回 `newAlerts`；`force=1` 忽略最短回源间隔 |
| POST | `/api/watch/history` | 清空监听历史记录（基线与「已提醒」表不动，清完不会把旧鸟再报一遍） |

> 监听的默认状态是**开着**的（`enabled: true`）：全新安装（`data/watch.json` 不存在）时状态里没有条件，
> 页面一打开就会把当前条件同步过去并自动建基线，同时给一句「已默认开启稀有监听（可在「我的」里关掉）」的提示。
> 服务端用一个 `everConfigured` 记号区分「从没配过」与「用户亲手关掉」—— 前者自动开，后者完全尊重用户的开关。

> 每个上游接口怎么调、参数与返回字段、以及和本地接口的对应关系，见 **[docs/接口说明.md](docs/接口说明.md)**。

`/api/hot` 还支持 `filter=all|protected|national|chinaEndemic`、`sort=record|protection`、`q=<关键词>`、`ensure=<预取等级的头部物种数>`；
任何区域类接口加上 `nocache=1` 可定向忽略缓存、强制回源（其余地区的缓存不受影响）。

**记录检索的三个条件**（实测上游 `record/activity/*` 与统计接口都认）：

| 前端字段 | 本地参数 | 上游参数 | 匹配方式 |
| --- | --- | --- | --- |
| 观测地点 | `pointname` | `pointname` | 关键字模糊匹配（填「奥森」能匹配到「奥林匹克森林公园（奥森）」） |
| 用户名称 | `username` | `username` | 记录人账号，精确匹配；不存在的用户返回 0 |
| 鸟种名称 | `taxonid` | `taxonid` | 由 `/api/taxon-resolve` 在**郑四名录**里把名字折算成 id 后再查 |

以「北京 · 当天」为例，各条件叠加后的实测口径：

| 条件 | 鸟种数 | 报告数 | 记录条数 |
| --- | --- | --- | --- |
| 北京（基准） | 152 | — | 1,415 |
| + 观测地点「奥森」 | 71 | 11 | 288 |
| + 用户「Zacco」 | 20 | — | — |
| + 鸟种「灰喜鹊」 | 1 | — | 1 |

**鸟种名称解析：郑四名录（`Z4`）**

上游 `taxon/search` 返回的每行都带一个 `version` 字段。实测全量 3098 行只有两个前缀：
`G3-…`（1503 行）与 `Z4-…`（1595 行）——**站点下拉框里写的 `CH4` 在数据里根本不存在**。
而榜单数据源 `record/activity/taxon` 认的 id 全落在 `Z4` 那一族（灰喜鹊 `4721`、喜鹊 `4734`、白头鹎 `4866`、麻雀 `5383`），
所以本项目把**「郑四」等价为 `version` 前缀 `Z4`**，`/api/taxon-resolve` 与 `/api/taxon-search` 都只在这一族里查。

这样做顺带解决了同名歧义：郑四名录里「喜鹊」只有 `4734`（`Pica serica`）一条，
不再出现 `G3` 族里 `700`（`Pica pica`）与它打架的情况。名录行还带 `pinyin` / `szm`（首字母）字段，
所以 `灰喜鹊` / `Cyanopica cyanus` / `huixique` / `hxq` 都能解析到同一个 id。
整份名录缓存 7 天，解析是纯内存查表。

**稀有度怎么算**：排序键是「该地区**最近两年**（去年 1 月 1 日起至今）的记录数」，
升序 —— 记录少才是「本地稀有」的信号，前三名就是本地区这两年最难见到的三笔记录。
同记录数时：国一 → 国二 → 三有 → 其余，最后按中文名，保证顺序稳定可复现。

每条还带一个 `rarity`（0~1）：用对数刻度把**历史记录数**映射成「稀有度」——
`rarity = 1 - ln(历史记录数+1) / ln(本地历史最多记录数+1)`，
若不取对数，「1 条」和「5 条」在长尾数据里几乎看不出差别。卡片底部的条就是它。

接口字段：`count` = 本时段记录数（成员口径），`historyCount` = 该地区最近两年记录数（排序口径），
`rarity` 由 `historyCount` 推出。`/api/taxons` 两者都带。

**历史取不到时会降级**：上游偶发风控 / 范围过大时，`stat.historyUsed` 会是 `false`、
`stat.historyError` 给出原因，此时榜单自动退回「按本时段记录数排序」，并在榜单脚注写明，
页面不会因此空白。失败结果**不会被缓存**。

**缓存**：榜单（本时段清单）用 `HOT_TTL_MS`、疑问标记用 `DOUBT_TTL_MS`，默认 24 小时（一天失效一次）；
历史稀有度用 `HISTORY_TTL_MS`，默认 **一个月**（口径固定、变化慢，一个地区一年基本只回源十几次），
与概览 / 趋势的 10 分钟互不影响。
页面上的缓存徽章会显示「TTL 1 天」。需要最新数据时点「刷新数据」（`nocache=1`），
它会强制回源榜单本时段清单、疑问标记与概览；**历史稀有度不吃 `nocache`** ——
一个月缓存是强制的，只按有效期自然过期（口径固定、变化慢，不需要跟着刷新）。

**报告明细分页（不再一次翻全）**：上游 `record/activity/search` 单页 `limit` 上限是 50，
早先的实现会翻满 10 页、去重后一次性返回给前端本地分页。现在改成**真正的上游分页**：
`/api/records` 只取当前这一页（`page` / `limit`），翻页一页一次请求，
既快也不容易踩到上游风控。弹层里会写明「上游共 N 份公开报告，本页 M 份」。
每页默认 **10 条**（与记录中心站点列表一致）；另实测**不传 `limit` 上游会直接 500**
（按「结果集过大」处理，连区县·单日都挂），所以每页条数必须显式传。

**概览卡下钻**：网页端的「记录鸟种数 / 观鸟报告数 / 鸟种记录条数 / 公开报告」四张卡可点击，弹出明细层。
「记录鸟种数 / 鸟种记录条数」直接取鸟种明细的同源口径（`stat.speciesCount / recordSum`），
因为上游 `record/taxon/num` 与 `record/activity/taxon` 更新不同步，混用会出现卡片与明细对不上的情况；
「观鸟报告数 / 公开报告」的下钻受上游限制：`record/activity/search` 只返回**公开报告**，
单页最多 50 条（本项目每页取 10 条），所以由服务端分页、按钮翻页。

**报告跳转链接怎么来的**：报告明细里点任意一行（或报告编号链接）会跳到上游详情页，
URL 规则是 `/home/record/page.html?param=<Base64(JSON({reportId,ts}))>&sign=<MD5>`。
站点页面用 `calcMD5(parseParam)` 校验 sign，而它的 `md5.js` 里 `str2blks_MD5` 直接读 `str.length` / `str.charCodeAt`，
传入普通对象时两者都取不到，实际等价于对空串求 MD5——即 `sign` 与 reportId 无关，恒为 `d41d8cd98f00b204e9800998ecf8427e`。
已用真实浏览器实测该链接可正常打开报告详情（无需登录）。

> **上游风控**：请求过于频繁时站点会返回 `{code:505, success:false}`（站点前端据此弹验证码）。
> 这类响应**不会被当成「空结果」写进缓存**——客户端会直接抛错，避免页面在整个 TTL 内一直显示 0。
> 页面遇到 505 时会在**应用内**弹出验证码浮层（`iframe` 内嵌官方验证页，不跳出应用；验证通过后顶部出现
> 「✓ 验证通过 · 关闭并返回主页面」），输一次即解封（按 IP 记，同一网络下的设备一起解封）。
> 浮层里也会透传上游 `msg` 的原文，便于判断到底是风控还是真的出错。

**侧栏图表**：逐月鸟种数 / 逐月报告数 / 地区排行三块默认隐藏（`web/index.html` 里 `#sideCols` 的 `hidden`）。
隐藏时前端会跳过趋势接口请求与 SVG 渲染；把 `hidden` 去掉即恢复双栏布局，无需改样式。

## 发布版本（打 tag 自动发布）

推一个 tag 就会自动构建 4 个产物并发布到 Releases，不需要手动跑任何构建命令：

```bash
git tag -a v0.0.3 -m "v0.0.3"     # -a 是附注标签，带作者 / 日期 / 说明
git push origin v0.0.3            # ← 必须单独推 tag，git push 不会顺带推它
```

约 3–5 分钟后自动完成。桌面三个平台**并行**构建（`windows-latest` / `macos-latest` arm64 /
`macos-15-intel` x64），每个平台都会：构建 → **冒烟验证**（解压发布包、真起一次那个二进制打
`/api/health`，不通就让整个 job 失败，坏包发不出去）→ 压成 zip。Android 是另一个 job，
在自己的 runner 上装 SDK / NDK、拉 nodejs-mobile、构建 APK，并验证**签名、清单、assets 是否齐全**。
最后再由一个单独的 job 把 4 个附件一次挂到 Release 上。

产物名取自 tag：

```
birdreport-rare-birds-<tag>-win-x64.zip
birdreport-rare-birds-<tag>-mac-arm64.zip
birdreport-rare-birds-<tag>-mac-x64.zip
birdreport-rare-birds-<tag>-android-arm64.apk
```

**tag 怎么写决定发布形态**：

| 写法 | 结果 |
| --- | --- |
| `v1.0.0`、`v0.0.3` | 正式 Release |
| `v0.0.3-beta`、`v1.0.0-rc1` | **Pre-release**（tag 里带 `-` 即自动标记为预发布） |

**几个注意点**

- **`git push` 不会推 tag**，必须 `git push origin <tag>`，否则工作流根本不触发。
- **别用 `git push --tags`**：它会把本地所有 tag 一次全推上去，包括你不打算发布的那些。
- **重复推同一个 tag 是安全的**：Release 已存在时，工作流只覆盖附件，既不会失败，也不会动你
  在网页上写好的发布说明与预发布标记。所以「先在网页建好 Release、写好说明，再打 tag 让 CI
  挂产物」这条流程也能走。
- **要重来**：`git tag -d v0.0.3` 删本地、`git push origin --delete v0.0.3` 删远端（会连带删掉
  对应的 Release）。若只是附件不对，**不必删 tag**，重推一次同一个 tag 即可。
- `package.json` 的 `version` 与发布**无关**（产物版本取自 tag）。想保持仓库里版本号一致，
  可以顺手 `npm version <版本> --no-git-tag-version`，再把 package.json 一起提交。

另有 `workflow_dispatch` 手动入口：在 Actions 页面点「Run workflow」只构建、把产物存成
artifact（不建 Release），用于试跑整条流程。

## 缓存策略

全项目只有**一套**缓存实现（`server/cache.mjs` 的 `LayeredCache`），两个实例复用同一套读写与落盘逻辑：

| 实例 | 文件 | TTL | 用途 |
| --- | --- | --- | --- |
| `api` | `data/api-cache.json` | 默认 **10 分钟**（`CACHE_TTL_MS` 可覆盖），**支持按条目单独指定** | 榜单 / 概览 / 趋势 / 地区排行 / 行政区字典 / 郑四名录 / 报告分页 |
| `protection` | `data/protection.json` | 永不过期 | 鸟种保护等级（参考数据，变化极少） |

`api` 实例里不同数据用不同的有效期（写入时按条目指定，互不影响）：

| 数据 | TTL | 环境变量 |
| --- | --- | --- |
| 榜单（地区鸟种清单） | **24 小时**（一天失效一次） | `HOT_TTL_MS` |
| 历史稀有度（该地区最近两年的记录数） | **一个月** | `HISTORY_TTL_MS` |
| 郑四名录（全量鸟种） | **7 天** | `CATALOG_TTL_MS` |
| 行政区字典（省 / 市 / 区县） | **一个月** | `DICT_TTL_MS` |
| 概览 / 趋势 / 地区排行 / 报告分页 | 10 分钟 | `CACHE_TTL_MS` |
| 降级结果（有子接口没取到） | 60 秒 | `DEGRADED_TTL_MS` |

**读写流程**

1. **写入**：结果先进内存 `Map`，同时防抖写盘（临时文件 + 原子替换，避免写坏）。
2. **读取**：直接命中内存，不做任何上游请求。
3. **重启**：启动时把本地文件**整体读入内存**当作缓存继续用，所以服务重启后第一次请求就可能是命中（实测 `/api/hot` 10ms 内返回，不触发上游调用）。
4. **过期**：读取时惰性判定 + 每 5 分钟批量剔除；过期条目自动回源并重新落盘。
5. **容量**：超过 `max` 按最久未使用淘汰；退出进程（SIGINT/SIGTERM/exit）前强制落盘。

**复用点（减少重复请求的关键）**

- 榜单的**原始数据**与「条数 / 筛选 / 排序 / 关键词」解耦：同一个地区只向上游取一次，切换 Top N、筛选条件、排序方式、搜索词都在缓存数据上重新计算（实测 4–6ms）。
- 保护等级字典按鸟种 id 全局共享：第一个地区补全后，其它地区、其它查询直接复用（全国 3098 种只需拉取一次）。
- 行政区字典（省/市/区县）被下拉框和地区排行两处共用，只取一次，缓存一个月。
- 同一 key 的并发请求会合并成一次上游调用，避免并发击穿。
- 页面右上方的「本地缓存 · N 分钟前 / 已从上游更新」徽章 + 榜单区的「刷新数据」按钮，能直接看到当前是复用缓存还是回源；`GET /api/cache` 可查看命中率、条数与上次落盘时间。

**实测**（同一地区 `top=50`）

| 场景 | 耗时 | 来源 |
| --- | --- | --- |
| 首次查询 | ~5.2s | 上游 |
| 再次查询 | ~4ms | 内存缓存 |
| 切换筛选 / 排序 | ~6ms | 内存缓存（同一份榜单数据） |
| 服务重启后首查 | ~10ms | 本地文件 → 内存缓存 |

## 实现说明

上游接口并非公开文档化的 REST API，前端对所有请求做了保护，本项目做了等价实现：

1. **请求体**：把参数按 key 升序排列后 `JSON.stringify`，再用站点内置 RSA 公钥做 PKCS#1 v1.5 加密；超过 117 字节按块加密后拼接（按 UTF-8 字节边界切分，避免截断中文）。
2. **请求头**：`timestamp` / `requestId` / `sign`，其中 `sign = MD5(json + requestId + timestamp)`。
3. **响应体**：`data` 字段为 AES-256-CBC 密文（base64），key / iv 取自站点 `aes.util.js` 扰码表还原后的明文。

### 缓存与限流

- 榜单缓存 **24 小时**（一天失效一次），概览 / 趋势 / 地区排行缓存 **10 分钟**，郑四名录缓存 **7 天**；
  全部持久化到本地、重启后读入内存继续复用（详见上文「缓存策略」）。
- 保护等级字典按鸟种 id 持久化到 `data/protection.json`，只增量补全缺失项；并发 4、每次请求间隔 60ms，避免对上游造成压力。
- 首次查询某区域时，会同步补全「最稀有的头部（默认前 200 种）」的等级，其余物种在后台慢慢补齐，后续请求即可命中。
- **辅助统计有等待上限**：概览的三个统计接口与趋势接口只影响概览卡与侧栏图表，上游一旦卡顿
  （`api()` 是 25 秒超时 × 2 次重试）会把整页查询拖到一分多钟。因此这些调用统一走 `within()` 限时
  （默认 15 秒，`STAT_TIMEOUT_MS` 可覆盖），超时先用兜底值渲染，榜单不受影响；
  兜底值只写 60 秒短缓存，避免「全 0」被按正常 TTL 缓存住。
- **鸟种名称解析不再依赖地区清单**：整份郑四名录（1595 条）缓存 7 天，解析是纯内存查表，
  不会为「认一个名字」额外打上游。前端另给了 8 秒上限，超时就放弃鸟种条件照常查询并提示可重试。
- **明确的业务错误码不重试**：上游返回 `code 500 / 505 / 405` 时 `api()` 会立即抛错（`noRetry`）。
  重试不能让它变好，而 `code 500` 本身要 20 秒才吐出来，重试 3 次会把一次失败拖成一分钟。

### Android 打包（为什么这么做）

桌面版那套「Node SEA 注入」在 Android 上走不通：Android 是个 Java/Kotlin 的世界，双击一个
可执行文件也不会发生什么。所以 Android 版是**把 Node 当成一个可链接的库**来用 ——
这正是 [nodejs-mobile](https://github.com/nodejs-mobile/nodejs-mobile) 提供的东西：

```
APK
├── lib/arm64-v8a/libnode.so      47 MB   ← nodejs-mobile 预编译的 Node 18.20.4（导出 node::Start）
├── lib/arm64-v8a/libbirdnode.so  0.1 MB  ← 我们自己的 JNI 壳：native-lib.cpp
├── lib/arm64-v8a/libc++_shared.so        ← libnode.so 依赖它，必须一起带上
└── assets/nodejs-project/               ← server/ 与 web/ 的原样副本
```

启动链条：

1. `MainActivity` 起一个子线程（Node 的事件循环不会返回，**绝不能**占着主线程）；
2. 子线程调 JNI（`NodeRunner.startNode`）→ `native-lib.cpp` 里设置好 `argv`、`BIRD_DATA_DIR`、
   `TMPDIR`、`HOST=127.0.0.1`，把 Node 的 stdout / stderr 用 `pipe` + `dup2` 接到 logcat
   （所以 `adb logcat -s BirdNode` 能看到它的一切输出），然后调用 `node::Start()`；
3. 首次启动时 `AssetInstaller` 已经把 `assets/nodejs-project/**` 解包到应用私有目录
   （assets 里的东西没有文件路径，而 Node 必须看到真实文件），并留一个 `.assets-version`
   标记 —— 只有版本变了才重解包。**数据目录 `files/data` 故意放在解包目录之外**，
   这样重解包不会把缓存一起清掉；
4. 主线程轮询 `/api/health`，通了才让 WebView 加载 `http://127.0.0.1:8787/`，
   加载完撤掉遮罩。

几个被 Android 逼出来的改动：

- **`BIRD_DATA_DIR` 环境变量**（见 `server/runtime.mjs`）：Android 进程的当前目录是 `/`，
  既不可写也谈不上「程序同级目录」，所以缓存位置必须显式告知。
- **明文 HTTP 只对回环地址开口**：Android 9（API 28）起默认禁止明文 HTTP，
  用 `res/xml/network_security_config.xml` 只给 `127.0.0.1` / `localhost` 开了例外，
  而不是图省事写 `usesCleartextTraffic="true"` 把整个 App 的 HTTP 限制（真机上那样等于对所有域名放开）。
- **退出直接杀进程**：Node 的事件循环没有「优雅退出」的口子，`onDestroy` 里
  `Process.killProcess(myPid())` —— 不这么做，下次打开时 8787 还占着，页面会白屏。
- **只出 arm64-v8a**：`libnode.so` 单个 ABI 就 47 MB，多带一个体积直接翻倍；
  而 2020 年之后的 Android 手机基本都是 64 位 ARM。

### 已知限制

- **Android 版只支持 64 位 ARM 手机**（`arm64-v8a`），且需要 Android 7.0（API 24）以上；
  模拟器与 Intel 版手机装不上（想支持就得改 `abiFilters` 并接受体积翻倍）。
- **Android 的「稀有监听」后台通知只在应用进程还活着时有效**。原因是架构使然：本地 Node 服务端与
  WebView 跑在**同一个进程**里，进程没了接口也就没了 —— 用 WorkManager 到点唤醒去问一个已死的本地端口
  没有意义，常驻前台服务又要一直挂一条「正在运行」的通知。所以按 Home 退到后台、进程还在时会照常提醒，
  从最近任务里划掉（或系统回收进程）之后就不再提醒。
  通知权限（Android 13+ 的运行时权限 `POST_NOTIFICATIONS`）在**打开监听开关时**申请一次；
  没授权也能用，只是退到后台不会提醒，「我的」面板里会明确写出来。
- **监听的判定依据是「该地区最近两年记录数 ≤ 稀有数量」，这是个绝对条数**，市级以上范围几乎命中不了
  （实测下界：北京市 95 条、朝阳区 64 条、全国 286 条）。「我的」面板里会摊开「本时段最稀有的也有 N 条」并给出建议值，
  默认的 ≤3 条只适合区县一级。
- **监听默认开着、条件自动跟随**：全新安装时页面一打开就按当前条件自动开起来。若想彻底关掉，
  在「我的」里关一次即可 —— 服务端会记住（`everConfigured`），之后不会再自动打开。
- **每轮检查都要强制回源**（榜单的本时段清单缓存 24 小时，照抄缓存的话一天都是同一份数据），
  但服务端有一道**最短回源间隔**（默认 30 分钟）挡住过密的请求 —— 前端按 10 分钟轮询，
  没到点的轮次直接复用上一轮结果、不会打上游。
- **全国范围可以查**，但**必须同时填起始日期与结束日期**。早先「上游不支持全国聚合」的判断是错的 ——
  那几次真因是 `505` 风控。选中「全国」时页面会立刻把这条要求写在日期框旁边，缺日期时不发请求。
  不带时间限制的全国查询数据量过大（实测无时间约 **1358 万条**：单日 0.8 万 / 一周 17.5 万 / 一个月 62.7 万），
  所以这一档被显式拦住，而不是放它去跑。全国口径较慢，首次约 30~60 秒（近两年基线实测 45 秒），结果会缓存复用。
- **上游也不支持「大范围 + 全时段」**：实测北京市不带任何时间约 20 秒后返回 `code 500`，「近 5 年」同样失败；
  「当天 / 近 30 天 / 近 1 年 / 近 3 年」都正常。所以起止日期默认「当天」，把两个日期都清空时页面会给出警告。
  （宽窗口本身也很重、偶发 500 —— 所以榜单的历史口径才固定成「最近两年」并缓存一个月，见上文「稀有度怎么算」。）
- 观鸟数据属于公民科学数据，存在明显的观鸟强度与地区采样偏差，「记录数少」既可能是真的稀有，也可能是**观测覆盖不足/识别难度高**，不建议直接当作种群数量或保护优先级结论。
- 保护等级字段来自上游数据源，覆盖《国家重点保护野生动物名录（2021）》、三有名录、IUCN 与中国生物多样性红色名录；个别鸟种可能缺等级或存在版本差异。
- 上游对 `record/activity/search`（报告明细）有访问频次风控，短时间翻页较多会返回 `code 505`；此时报告明细会如实报错而**不会**被缓存成「0 份报告」，稍等几分钟再试即可。
- 榜单按时段查询时，上游可能对同一鸟种给出**两个名录版本的 id**（如灰喜鹊 `689`/`4721`），时间跨度越大越容易出现。
  按名解析已限定在郑四（`Z4`）名录，不会再踩这个坑；但**时段很宽时榜单本身仍可能出现同名两行**——
  这**不全是重复数据**：「喜鹊」的两个版本分别是 `Pica serica`（东亚喜鹊）与 `Pica pica`（欧亚喜鹊），是分类学拆分后的两个不同种。
