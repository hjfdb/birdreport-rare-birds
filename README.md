# 观鸟地区稀有鸟种榜

基于 **中国观鸟记录中心**（[birdreport.cn](https://www.birdreport.cn/)）公开数据的「按行政区汇总本地稀有鸟种」服务，包含一个 **Node.js 服务端** 和一个 **网页端**。

选定 省 / 市 / 区县 与起止日期后（默认 **当天**），页面会把该区域**记录数最少的鸟种排在最前面**——记录越少，说明这种鸟在本地越稀有；同时标注每种鸟的保护等级（《国家重点保护野生动物名录》国家一级 / 国家二级 / 三有名录）、IUCN 红色名录等级、是否中国特有。

**榜单的两个口径是分开的**（这是本项目最关键的设计）：

| | 数据源 | 作用 |
| --- | --- | --- |
| **成员**：这段时间里出现过哪些鸟 | `record/activity/taxon` **带**起止日期 | 榜单显示哪些卡片 |
| **稀有度**：谁更稀有 | `record/activity/taxon` **不带**时间范围（该地区历史全时段） | 榜单的排序与稀有度条 |

为什么必须分开：时间窗口一窄（例如「当天」），几乎所有鸟种都只有 1 条记录，排序就完全没有信息量。
实测「北京 · 当天」有 **41 种鸟都只记录到 1 条**；换用历史口径后，同样是这 152 种鸟，前五位的历史记录数变成
**1 / 76 / 109 / 153 / 158 条**——「这种鸟在北京历史上总共只被记录过 1 次」才是真正的稀有信号。
两个口径各存一份缓存，互不影响。

## 快速开始

### 方式一：直接下载 exe（不用装 Node）

到 **[Releases](../../releases/latest)** 下载 `birdreport-rare-birds-vX.Y.Z-win-x64.zip`，
解压出 `观鸟地区稀有榜-vX.Y.Z-win-x64.exe` 后双击运行 ——
浏览器会自动打开 <http://127.0.0.1:8787/>，关掉那个黑色控制台窗口即停止服务。
缓存落在 exe 同级的 `data/` 目录（该位置不可写时退到用户数据目录）。

> **这个 exe 没有代码签名**：它由 Node 官方 SEA 机制注入生成，注入会让 node.exe 原有的
> 签名失效，而签一份自己的证书需要额外成本。首次运行时 Windows SmartScreen 可能提示
> 「未知发布者」，点「更多信息 → 仍要运行」即可。介意的话可以按方式三自己构建。

### 方式二：从源码跑

```bash
# 无需 npm install（零第三方依赖，仅用 Node 内置模块）
node server/index.mjs
```

启动后打开：<http://127.0.0.1:8787/>

可用环境变量：`PORT`（默认 8787）、`HOST`（默认 127.0.0.1）。

### 方式三：自己构建 exe

```bash
npm install          # 装两个构建期依赖（esbuild、postject），它们不会进 exe
npm run build:exe    # 产物在 dist/，可用 EXE_NAME 环境变量改文件名
```

构建走 Node 官方的 SEA：`server/` 打成单文件 CJS、`web/` 内嵌成资源、再复制一份 node.exe
把 blob 注入进去 —— 所以**产物里跑的 Node 就是构建机上那一个**，换大版本等于换运行时。

> 打一个 tag 就会由 GitHub Actions 自动构建并发布到 Releases，不用手动跑上面的命令 ——
> 详见下文「发布版本」。

## 功能

**网页端**

- 省 / 市 / 区县 三级联动 + 起始 / 结束日期（默认 **当天**；**没有**「近 7 天 / 近 1 年」这类档位按钮，直接填日期即可）
- **记录检索（顶部查询栏）**：观测地点 / 用户名称 / 鸟种名称三个条件，与省市、时间一起下推到上游，
  概览卡、稀有榜、报告明细会一起收窄（例：北京 · 奥森 · Zacco · 灰喜鹊 的记录）；
  鸟种名称在**郑四名录**里解析，支持中文名 / 学名 / 英文名 / 拼音 / 首字母，命中多个不同鸟种时列出候选让人选，条件同时写入地址栏
- 概览统计卡：鸟种数、目 / 科、观鸟报告数、鸟种记录条数、公开报告（前四张可点击下钻明细）
- 保护等级构成：国家一级 / 国家二级 / 三有 / 中国特有 / IUCN 受威胁(CR/EN/VU)
- **本地稀有鸟种排行**：**每行 5 个卡片、展示该时段全部鸟种**（不按 Top N 截断）。
  卡片上的大数字是**该地区历史全时段记录数**（排序依据），下面一行注明本时段记录数；
  底部「稀有度」条同样按历史口径，带目科信息与保护等级徽章。卡片只做展示，**点鸟种不再弹出报告**
- 筛选：全部 / 仅受保护 / 仅国家重点保护 / 仅中国特有，以及按鸟种名、学名搜索
- 图表：逐月鸟种数、逐月报告数、省内下一级（地市或区县）鸟种数排行（三块默认隐藏，见下）
- 榜单 CSV 导出（含保护等级列，UTF-8 BOM，Excel 可直接打开）
- 支持 URL 直达：`?province=浙江省&city=杭州市&district=西湖区&start=2026-01-01&end=2026-10-10`
  （`all=1` 表示全部时间）

**REST 接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/provinces` | 省级行政区字典 |
| GET | `/api/cities?provinceCode=` | 地级行政区字典 |
| GET | `/api/districts?cityCode=` | 区县字典 |
| GET | `/api/overview?province=&city=&district=&startTime=&endTime=` | 区域概览统计 |
| GET | `/api/hot?…&filter=all&sort=record&q=` | 本地稀有鸟种排行：成员取当前时段，排序按该地区历史全时段记录数（不传 `top` 即返回全部） |
| GET | `/api/taxons?…&sort=record&limit=500` | 完整鸟种明细（成员与榜单一致；每条带 `historyCount`，同样按历史稀有度排序） |
| GET | `/api/records?…&page=1&limit=50` | 公开报告明细（**只取上游一页**，默认 50 条） |
| GET | `/api/trend?…` | 逐月鸟种数 / 报告数 |
| GET | `/api/province-rank?version=CH4` | 全国各省鸟种数排行 |
| GET | `/api/region-rank?province=&city=&level=city\|district` | 省内下一级地区鸟种数 |
| GET | `/api/taxon-search?q=` | 郑四名录检索（中文名 / 学名 / 英文名 / 拼音 / 首字母） |
| GET | `/api/taxon-resolve?name=` | 鸟种名称 → `taxon_id`（在郑四名录里解析，带候选） |
| GET | `/api/taxon-level?id=` | 单个鸟种的保护等级 |
| GET | `/api/cache` | 缓存策略与命中情况总览 |
| POST | `/api/cache/flush` | 立即把缓存落盘 |
| POST | `/api/cache/clear` | 清空接口结果缓存（保护等级字典不受影响） |
| GET | `/api/protection/status` | 保护等级字典缓存进度 |
| POST | `/api/protection/sync` | 后台预热全部鸟种的保护等级 |
| GET | `/api/health` | 健康检查 |

> 每个上游接口怎么调、参数与返回字段、以及和本地接口的对应关系，见 **[docs/接口说明.md](docs/接口说明.md)**。

`/api/hot` 还支持 `filter=all|protected|national|chinaEndemic`、`sort=record|protection`、`q=<关键词>`、`ensure=<预取等级的头部物种数>`；
任何区域类接口加上 `nocache=1` 可定向忽略缓存、强制回源（其余地区的缓存不受影响）。

**记录检索的三个条件**（实测上游 `record/activity/*` 与统计接口都认）：

| 前端字段 | 本地参数 | 上游参数 | 匹配方式 |
| --- | --- | --- | --- |
| 观测地点 | `pointname` | `pointname` | 关键字模糊匹配（填「奥森」能匹配到「奥林匹克森林公园（奥森）」） |
| 用户名称 | `username` | `username` | 记录人账号，精确匹配；不存在的用户返回 0 |
| 鸟种名称 | `taxonid` | `taxonid` | 由 `/api/taxon-resolve` 在**郑四名录**里把名字折算成 id 后再查 |

以「北京 · 当天」为例，各条件叠加后的实测口径：

| 条件 | 鸟种数 | 报告数 | 记录条数 |
| --- | --- | --- | --- |
| 北京（基准） | 152 | — | 1,415 |
| + 观测地点「奥森」 | 71 | 11 | 288 |
| + 用户「Zacco」 | 20 | — | — |
| + 鸟种「灰喜鹊」 | 1 | — | 1 |

**鸟种名称解析：郑四名录（`Z4`）**

上游 `taxon/search` 返回的每行都带一个 `version` 字段。实测全量 3098 行只有两个前缀：
`G3-…`（1503 行）与 `Z4-…`（1595 行）——**站点下拉框里写的 `CH4` 在数据里根本不存在**。
而榜单数据源 `record/activity/taxon` 认的 id 全落在 `Z4` 那一族（灰喜鹊 `4721`、喜鹊 `4734`、白头鹎 `4866`、麻雀 `5383`），
所以本项目把**「郑四」等价为 `version` 前缀 `Z4`**，`/api/taxon-resolve` 与 `/api/taxon-search` 都只在这一族里查。

这样做顺带解决了同名歧义：郑四名录里「喜鹊」只有 `4734`（`Pica serica`）一条，
不再出现 `G3` 族里 `700`（`Pica pica`）与它打架的情况。名录行还带 `pinyin` / `szm`（首字母）字段，
所以 `灰喜鹊` / `Cyanopica cyanus` / `huixique` / `hxq` 都能解析到同一个 id。
整份名录缓存 7 天，解析是纯内存查表。

**稀有度怎么算**：排序键是「该地区**历史全时段**的记录数」（不带时间范围的 `recordcount`），
升序 —— 记录少才是「本地稀有」的信号，前三名就是本地区历史上最难见到的三笔记录。
同记录数时：国一 → 国二 → 三有 → 其余，最后按中文名，保证顺序稳定可复现。

每条还带一个 `rarity`（0~1）：用对数刻度把**历史记录数**映射成「稀有度」——
`rarity = 1 - ln(历史记录数+1) / ln(本地历史最多记录数+1)`，
若不取对数，「1 条」和「5 条」在长尾数据里几乎看不出差别。卡片底部的条就是它。

接口字段：`count` = 本时段记录数（成员口径），`historyCount` = 该地区历史全时段记录数（排序口径），
`rarity` 由 `historyCount` 推出。`/api/taxons` 两者都带。

**历史取不到时会降级**：上游偶发风控 / 范围过大时，`stat.historyUsed` 会是 `false`、
`stat.historyError` 给出原因，此时榜单自动退回「按本时段记录数排序」，并在榜单脚注写明，
页面不会因此空白。失败结果**不会被缓存**。

**缓存 24 小时（一天失效一次）**：榜单（本时段清单）用 `HOT_TTL_MS`，
历史稀有度用 `HISTORY_TTL_MS`，默认都是 24 小时，与概览 / 趋势的 10 分钟互不影响。
页面上的缓存徽章会显示「TTL 1 天」。需要最新数据时点「刷新数据」（`nocache=1`）。

**报告明细分页（不再一次翻全）**：上游 `record/activity/search` 单页 `limit` 上限是 50，
早先的实现会翻满 10 页、去重后一次性返回给前端本地分页。现在改成**真正的上游分页**：
`/api/records` 只取当前这一页（`page` / `limit`），翻页一页一次请求，
既快也不容易踩到上游风控。弹层里会写明「上游共 N 份公开报告，本页 M 份」。

**概览卡下钻**：网页端的「记录鸟种数 / 观鸟报告数 / 鸟种记录条数 / 公开报告」四张卡可点击，弹出明细层。
「记录鸟种数 / 鸟种记录条数」直接取鸟种明细的同源口径（`stat.speciesCount / recordSum`），
因为上游 `record/taxon/num` 与 `record/activity/taxon` 更新不同步，混用会出现卡片与明细对不上的情况；
「观鸟报告数 / 公开报告」的下钻受上游限制：`record/activity/search` 只返回**公开报告**，
单页最多 50 条，所以由服务端分页、按钮翻页。

**报告跳转链接怎么来的**：报告明细里点任意一行（或报告编号链接）会跳到上游详情页，
URL 规则是 `/home/record/page.html?param=<Base64(JSON({reportId,ts}))>&sign=<MD5>`。
站点页面用 `calcMD5(parseParam)` 校验 sign，而它的 `md5.js` 里 `str2blks_MD5` 直接读 `str.length` / `str.charCodeAt`，
传入普通对象时两者都取不到，实际等价于对空串求 MD5——即 `sign` 与 reportId 无关，恒为 `d41d8cd98f00b204e9800998ecf8427e`。
已用真实浏览器实测该链接可正常打开报告详情（无需登录）。

> **上游风控**：请求过于频繁时站点会返回 `{code:505, success:false}`（站点前端据此弹验证码）。
> 这类响应**不会被当成「空结果」写进缓存**——客户端会直接抛错，避免页面在整个 TTL 内一直显示 0。
> 遇到时稍等几分钟再试即可。

**侧栏图表**：逐月鸟种数 / 逐月报告数 / 地区排行三块默认隐藏（`web/index.html` 里 `#sideCols` 的 `hidden`）。
隐藏时前端会跳过趋势接口请求与 SVG 渲染；把 `hidden` 去掉即恢复双栏布局，无需改样式。

## 目录结构

```
├── server/
│   ├── birdreport.mjs   # 上游接口客户端（RSA 请求加密 + MD5 签名 + AES 响应解密）
│   ├── cache.mjs        # 统一缓存：磁盘持久化 + 启动读入内存 + TTL 过期
│   ├── protection.mjs   # 保护等级字典（复用同一缓存，永不过期）
│   └── index.mjs        # HTTP 服务、路由与静态托管
├── web/                 # 纯原生 HTML / CSS / JS 前端（零依赖，图表为内联 SVG）
├── .github/workflows/   # release.yml：打 tag 自动构建并发布 Release（见下文「发布版本」）
├── build-exe.mjs        # 打包单文件 exe（Node SEA）；build-exe.cmd 是同一流程的命令行版
└── data/                # 本地缓存文件（api-cache.json / protection.json，可随时删除，会自动重建）
```

## 发布版本（打 tag 自动发布）

推一个 tag 就会自动构建 exe 并发布到 Releases，不需要手动跑任何构建命令：

```bash
git tag -a v0.0.3 -m "v0.0.3"     # -a 是附注标签，带作者 / 日期 / 说明
git push origin v0.0.3            # ← 必须单独推 tag，git push 不会顺带推它
```

约 1–2 分钟后自动完成：构建 exe → **冒烟验证**（真起一次 exe 打 `/api/health`，不通就让整个
job 失败，坏包发不出去）→ 压成 zip → 建 Release 挂上附件。产物名取自 tag：
`birdreport-rare-birds-<tag>-win-x64.zip`。

**tag 怎么写决定发布形态**：

| 写法 | 结果 |
| --- | --- |
| `v1.0.0`、`v0.0.3` | 正式 Release |
| `v0.0.3-beta`、`v1.0.0-rc1` | **Pre-release**（tag 里带 `-` 即自动标记为预发布） |

**几个注意点**

- **`git push` 不会推 tag**，必须 `git push origin <tag>`，否则工作流根本不触发。
- **别用 `git push --tags`**：它会把本地所有 tag 一次全推上去，包括你不打算发布的那些。
- **重复推同一个 tag 是安全的**：Release 已存在时，工作流只覆盖附件，既不会失败，也不会动你
  在网页上写好的发布说明与预发布标记。所以「先在网页建好 Release、写好说明，再打 tag 让 CI
  挂产物」这条流程也能走。
- **要重来**：`git tag -d v0.0.3` 删本地、`git push origin --delete v0.0.3` 删远端（会连带删掉
  对应的 Release）。若只是附件不对，**不必删 tag**，重推一次同一个 tag 即可。
- `package.json` 的 `version` 与发布**无关**（产物版本取自 tag）。想保持仓库里版本号一致，
  可以顺手 `npm version <版本> --no-git-tag-version`，再把 package.json 一起提交。

另有 `workflow_dispatch` 手动入口：在 Actions 页面点「Run workflow」只构建、把产物存成
artifact（不建 Release），用于试跑整条流程。

## 缓存策略

全项目只有**一套**缓存实现（`server/cache.mjs` 的 `LayeredCache`），两个实例复用同一套读写与落盘逻辑：

| 实例 | 文件 | TTL | 用途 |
| --- | --- | --- | --- |
| `api` | `data/api-cache.json` | 默认 **10 分钟**（`CACHE_TTL_MS` 可覆盖），**支持按条目单独指定** | 榜单 / 概览 / 趋势 / 地区排行 / 行政区字典 / 郑四名录 / 报告分页 |
| `protection` | `data/protection.json` | 永不过期 | 鸟种保护等级（参考数据，变化极少） |

`api` 实例里不同数据用不同的有效期（写入时按条目指定，互不影响）：

| 数据 | TTL | 环境变量 |
| --- | --- | --- |
| 榜单（地区鸟种清单） | **24 小时**（一天失效一次） | `HOT_TTL_MS` |
| 郑四名录（全量鸟种） | **7 天** | `CATALOG_TTL_MS` |
| 概览 / 趋势 / 地区排行 / 字典 / 报告分页 | 10 分钟 | `CACHE_TTL_MS` |
| 降级结果（有子接口没取到） | 60 秒 | `DEGRADED_TTL_MS` |

**读写流程**

1. **写入**：结果先进内存 `Map`，同时防抖写盘（临时文件 + 原子替换，避免写坏）。
2. **读取**：直接命中内存，不做任何上游请求。
3. **重启**：启动时把本地文件**整体读入内存**当作缓存继续用，所以服务重启后第一次请求就可能是命中（实测 `/api/hot` 10ms 内返回，不触发上游调用）。
4. **过期**：读取时惰性判定 + 每 5 分钟批量剔除；过期条目自动回源并重新落盘。
5. **容量**：超过 `max` 按最久未使用淘汰；退出进程（SIGINT/SIGTERM/exit）前强制落盘。

**复用点（减少重复请求的关键）**

- 榜单的**原始数据**与「条数 / 筛选 / 排序 / 关键词」解耦：同一个地区只向上游取一次，切换 Top N、筛选条件、排序方式、搜索词都在缓存数据上重新计算（实测 4–6ms）。
- 保护等级字典按鸟种 id 全局共享：第一个地区补全后，其它地区、其它查询直接复用（全国 3098 种只需拉取一次）。
- 行政区字典（省/市/区县）被下拉框和地区排行两处共用，只取一次。
- 同一 key 的并发请求会合并成一次上游调用，避免并发击穿。
- 页面右上方的「本地缓存 · N 分钟前 / 已从上游更新」徽章 + 榜单区的「刷新数据」按钮，能直接看到当前是复用缓存还是回源；`GET /api/cache` 可查看命中率、条数与上次落盘时间。

**实测**（同一地区 `top=50`）

| 场景 | 耗时 | 来源 |
| --- | --- | --- |
| 首次查询 | ~5.2s | 上游 |
| 再次查询 | ~4ms | 内存缓存 |
| 切换筛选 / 排序 | ~6ms | 内存缓存（同一份榜单数据） |
| 服务重启后首查 | ~10ms | 本地文件 → 内存缓存 |

## 实现说明

上游接口并非公开文档化的 REST API，前端对所有请求做了保护，本项目做了等价实现：

1. **请求体**：把参数按 key 升序排列后 `JSON.stringify`，再用站点内置 RSA 公钥做 PKCS#1 v1.5 加密；超过 117 字节按块加密后拼接（按 UTF-8 字节边界切分，避免截断中文）。
2. **请求头**：`timestamp` / `requestId` / `sign`，其中 `sign = MD5(json + requestId + timestamp)`。
3. **响应体**：`data` 字段为 AES-256-CBC 密文（base64），key / iv 取自站点 `aes.util.js` 扰码表还原后的明文。

### 缓存与限流

- 榜单缓存 **24 小时**（一天失效一次），概览 / 趋势 / 地区排行缓存 **10 分钟**，郑四名录缓存 **7 天**；
  全部持久化到本地、重启后读入内存继续复用（详见上文「缓存策略」）。
- 保护等级字典按鸟种 id 持久化到 `data/protection.json`，只增量补全缺失项；并发 4、每次请求间隔 60ms，避免对上游造成压力。
- 首次查询某区域时，会同步补全「最稀有的头部（默认前 200 种）」的等级，其余物种在后台慢慢补齐，后续请求即可命中。
- **辅助统计有等待上限**：概览的三个统计接口与趋势接口只影响概览卡与侧栏图表，上游一旦卡顿
  （`api()` 是 25 秒超时 × 2 次重试）会把整页查询拖到一分多钟。因此这些调用统一走 `within()` 限时
  （默认 15 秒，`STAT_TIMEOUT_MS` 可覆盖），超时先用兜底值渲染，榜单不受影响；
  兜底值只写 60 秒短缓存，避免「全 0」被按正常 TTL 缓存住。
- **鸟种名称解析不再依赖地区清单**：整份郑四名录（1595 条）缓存 7 天，解析是纯内存查表，
  不会为「认一个名字」额外打上游。前端另给了 8 秒上限，超时就放弃鸟种条件照常查询并提示可重试。
- **明确的业务错误码不重试**：上游返回 `code 500 / 505 / 405` 时 `api()` 会立即抛错（`noRetry`）。
  重试不能让它变好，而 `code 500` 本身要 20 秒才吐出来，重试 3 次会把一次失败拖成一分钟。

### 已知限制

- **上游不支持全国范围的鸟种聚合查询**（返回 500）。选中「全国」时，页面会提示并改用「全国各省鸟种数排行」呈现，概览与榜单需选择具体行政区。
- **上游也不支持「大范围 + 全时段」**：实测北京市不带任何时间约 20 秒后返回 `code 500`，「近 5 年」同样失败；
  「当天 / 近 30 天 / 近 1 年 / 近 3 年」都正常。所以起止日期默认「当天」，把两个日期都清空时页面会给出警告。
- 观鸟数据属于公民科学数据，存在明显的观鸟强度与地区采样偏差，「记录数少」既可能是真的稀有，也可能是**观测覆盖不足/识别难度高**，不建议直接当作种群数量或保护优先级结论。
- 保护等级字段来自上游数据源，覆盖《国家重点保护野生动物名录（2021）》、三有名录、IUCN 与中国生物多样性红色名录；个别鸟种可能缺等级或存在版本差异。
- 上游对 `record/activity/search`（报告明细）有访问频次风控，短时间翻页较多会返回 `code 505`；此时报告明细会如实报错而**不会**被缓存成「0 份报告」，稍等几分钟再试即可。
- 榜单按时段查询时，上游可能对同一鸟种给出**两个名录版本的 id**（如灰喜鹊 `689`/`4721`），时间跨度越大越容易出现。
  按名解析已限定在郑四（`Z4`）名录，不会再踩这个坑；但**时段很宽时榜单本身仍可能出现同名两行**——
  这**不全是重复数据**：「喜鹊」的两个版本分别是 `Pica serica`（东亚喜鹊）与 `Pica pica`（欧亚喜鹊），是分类学拆分后的两个不同种。
