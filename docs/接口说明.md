# 上游接口使用说明

本项目的数据全部来自 **中国观鸟记录中心**（`www.birdreport.cn` / `api.birdreport.cn`）。
本文说明这些接口**怎么调、参数是什么、返回什么、在本项目里用来做什么**。

代码位置：所有上游调用集中在 [`server/birdreport.mjs`](../server/birdreport.mjs)，业务组装在 [`server/index.mjs`](../server/index.mjs)。

---

## 一、统一的调用约定

上游所有接口都是 `POST https://api.birdreport.cn/<path>`，并且**共用同一套保护机制**，与调用哪个接口无关：

| 环节 | 做法 |
| --- | --- |
| 请求体 | 把参数按 key 升序排列后 `JSON.stringify`，用站点 RSA 公钥做 **PKCS#1 v1.5 加密**；超过 117 字节按块加密，密文按字节拼接后再整体 base64 |
| 请求头 | `timestamp`（毫秒）、`requestId`（16 位随机串）、`sign = MD5(json + requestId + timestamp)` |
| 其他头 | `Content-Type: application/x-www-form-urlencoded; charset=UTF-8`、`Origin`/`Referer` 指向站点 |
| 响应 | `{ code, count, data }`，`data` 是 **AES-256-CBC** 密文（base64），解密后才是真正的 JSON |

这些细节封装在 `api(path, params)` 一个函数里，改接口时只需关心 `path` 和 `params`：

```js
import { api } from './server/birdreport.mjs';

const r = await api('/front/record/activity/taxon', {
  province: '北京市', startTime: '2026-10-10', endTime: '2026-10-10', page: 1, limit: 2000,
});
console.log(r.count, r.data[0]);
```

### 三个通用坑

1. **部分接口不套 `{code,data}` 外壳**，直接返回裸数组（如 `/front/province/summary/chart`）或裸对象（如 `/front/record/chart/summary`）。客户端已统一归一化成 `{code, success, count, data}`，所以上层不用判断。
2. **多块 RSA 加密不能把每块的 base64 直接拼接**，必须在字节层面 `concat` 后再整体编码，否则签名校验会返回「无效签名，验证签名失败」。
3. **中文明文必须按 UTF-8 字节边界切块**，否则会被截断成乱码。

### 地区参数的口径

`where` 条件在接口间通用，本项目用到的字段：

| 字段 | 说明 |
| --- | --- |
| `province` | 省名，如 `北京市`、`浙江省` |
| `city` | 市名，如 `杭州市`。**直辖市**该值等于省名，可省略 |
| `district` | 区县名，如 `西湖区` |
| `startTime` / `endTime` | `YYYY-MM-DD`，**可以传同一天**（单日查询）。两个都不传 = 全时段，但**大范围全时段聚合会失败**（见下方警告） |
| `version` | 名录版本。站点下拉框写 `CH4`=《中国鸟类分类与分布名录(第四版-郑四)》、`G3`=《中国观鸟年报-中国鸟类名录3.0版》。⚠️ 实测 `taxon/search` 返回的 `version` 字段里**只有 `G3-<hash>`（1503 行）与 `Z4-<hash>`（1595 行）两个前缀，没有 CH4**；而 `record/activity/taxon` 用到的 id 全部落在 `Z4` 那一族，所以本项目把「郑四」等价为前缀 **`Z4`** |

> ⚠️ **两个范围限制（实测）**
> 1. 全国范围查询（不传 `province`）会让上游返回 `500 系统内部异常`，本项目已在服务端短路，改为用「全国各省排行」呈现。
> 2. **大范围 + 全时段**也会返回 `500`：北京市「不带任何时间」约 20 秒后失败，「近 5 年」同样失败；而「当天 / 近 30 天 / 近 1 年 / 近 3 年」都能正常返回。所以页面的起止日期默认填「当天」，日期留空时会在时间提示行里给出警告。

## 二、接口清单与用途

### 1. 行政区字典（3 个）

| 上游接口 | 参数 | 返回 | 本项目用途 |
| --- | --- | --- | --- |
| `/front/system/adcode/province` | 无 | `[{province_code, province_name}]` ×34 | 省下拉框 |
| `/front/system/adcode/city` | `province_code` | `[{city_name, city_code}]` | 市下拉框；地区排行 |
| `/front/system/adcode/district` | `city_code` | `[{district_name, district_code}]` | 区县下拉框 |

- 必须用 **code**（`110000`）而不是名称去查下级。
- 直辖市的 `city` 只有一条（北京市 → 北京市），前端会自动选中，让查询直接下钻到区县。

### 2. 区域鸟种清单 —— 稀有榜的核心

```
POST /front/record/activity/taxon
params: { province, city, district, startTime, endTime, page, limit,
          pointname?, username?, taxonid? }
```

返回 `count`（鸟种总数）与数组：

```json
{
  "taxon_id": 4040,
  "taxonname": "环颈雉",
  "latinname": "Phasianus colchicus",
  "englishname": "Common Pheasant",
  "taxonordername": "鸡形目",
  "taxonfamilyname": "雉科",
  "recordcount": 5
}
```

**这是整个项目最关键的一个接口**：`recordcount` = 该鸟种在「该地区 + 该时段」内被记录的条数。一次 `limit=2000` 即可取全（全国最大的省也只有 700 多种）。

榜单口径：**按 `recordcount` 升序**——记录最少说明在本地最稀有，排最前面；
同记录数时先看保护级别（国一 → 国二 → 三有 → 其余），最后按中文名，保证顺序稳定可复现。
（上游本身不支持按此排序，返回顺序是 `taxon_id` 升序，排序全部在本地做。）

注意事项：
- 榜单原始数据与「筛选 / 排序」解耦——同一个地区只调一次，其余都在本地重算。
- 榜单缓存 TTL 是 **24 小时**（一天失效一次），与统计接口的 10 分钟分开设置。

**额外的四个过滤参数（顶部「记录检索」用的就是它们，已实测）**：

| 参数 | 含义 | 匹配方式 | 北京·当天实测 |
| --- | --- | --- | --- |
| `pointname` | 观鸟点名称 | 模糊 / 精确由 `mode` 决定（见下） | 不传 152 种；`奥森` → 71 种（匹配到「奥林匹克森林公园（奥森）」） |
| `username` | 记录人账号 | 模糊 / 精确由 `mode` 决定（见下） | `Zacco` → 20 种；不存在的用户 → 空集（不报错） |
| `taxonid` | 鸟种 id | 精确 | 只返回该鸟种（`count` 变 1），可与上面两个叠加 |
| `mode` | **整条查询**的匹配方式 | 不传或 `0` = 模糊；`1` = 精确 | 见下 |

叠加示例：`province=北京市&city=北京市&pointname=奥森&username=Zacco&taxonid=4721` → 1 种 / 1 条记录。

#### `mode`：整条查询的匹配方式（`pointname` 和 `username` 共用）

这是实打实踩过的坑。站点页面上那个下拉框（`<select name="mode">`，空 / `0` 模糊 / `1` 精确）
是**整条查询**的匹配方式，**同时作用于 `pointname` 与 `username`** —— 没法只让其中一个精确。

- 不传 `mode`（或传 `""` / `0` / `2`）→ **模糊匹配**；
- 传 `mode=1` → **精确匹配**。

实测（用户 `kkia`，只带 `username`、不带地区与时间）：

| 请求 | 返回 |
| --- | --- |
| 不传 `mode` | 229 行 / 229 种 |
| `mode=0`、`mode=""`、`mode=2` | 229 行 / 229 种（与不传相同） |
| **`mode=1`** | **212 行 / 212 种** ← 真身 |

精确结果是模糊结果的**真子集**（已验证），多出来的那 17 种（毛脚燕、赤麻鸭、灰斑鸠、普通雨燕、
红嘴鸥…）来自**别的用户名** —— 名字里含 `kkia` 子串的人。也就是说：

> 不指定 `mode` 时，绑定「kkia」会把邻居的鸟种也算成「已加新」，凭空少报一批「未加新」，
> 而页面看上去一切正常。

另外三个要点：

- `username` 也**大小写敏感**（`KKIA` → 0 种）；上游对不存在的用户名是**正常返回空集**（不报错），
  所以「空名单」必须当成失败处理，不能当成「这个人一种鸟都没见过」。
- `mode=1` 与 `province` 同时传也成立（福建省 `kkia` → 211 种，与不传 `mode` 相同，
  说明那个用户的活动范围本来就集中在福建；`mode` 的效果在**不带地区**的全量查询上才看得出来）。
- **一个请求就能取全**，不需要遍历 34 个省：逐省并集 = 212 种，与一次全国查询的差集为 0；
  分页核对（`limit=200`）→ 200 + 12 = 212，没有隐藏上限。
  注意别和「**不带 `username`** 的全国查询」搞混，那种查询上游会 500（结果集是全国所有鸟种）。

#### `outside_type`：被上游标疑的「疑问数据」

`outside_type` **不是返回字段，而是一个记录级的筛选条件**——这是最容易搞错的地方。
传 `outside_type=1` 时，接口只统计**被标疑的那些记录**，仍然返回鸟种行（带各自的 `recordcount`），
但行里**没有** `outside_type` 这个键，所以不能指望从返回数据里读它。

站点那边的做法能反推这个约定：在 `taxon.html` 的模板里是
`d.outside_type == 0 ? 中文名 : '<span style="color:#FF4040">中文名</span>'` ——
也就是说它对**同一批鸟种**做了两次查询（`outside_type=0` 与 `outside_type=1`），
再用红色标出后者的那些行。

本项目照这个思路实现（`server/index.mjs`）：

- 榜单主查询不带 `outside_type`（拿到该时段全部鸟种与总数）；
- 另发一次 `outside_type=1` 的查询，得到「疑问鸟种 → 疑问记录数」映射，单独缓存；
- 前端据此把鸟名标红、给出「疑问 N 条」，并把本时段记录数拆成
  **`正常 = 总数 - 疑问` · `疑问 = 疑问`**（逐种核对「正常 + 疑问 == 总数」）；
- 这次查询失败**不影响榜单**：只丢红色标记，脚注提示「疑问数据标记暂时取不到」，
  绝不会因为一个附加标记把整页打成错误。

#### `needRange`：全国范围必须同时给起止日期（本地约定，非上游参数）

选「全国」（不传 `province`）时，本服务端的区域类接口（`/api/hot`、`/api/overview`、`/api/records`、
`/api/trend`、`/api/taxons`）在**缺少 `startTime` / `endTime` 任一项**时会直接返回
`{ unsupported: true, needRange: true }` 并附一份空结果，**不打上游**。

原因不是「上游不支持全国」（早先这个判断是错的，那几次真因是 `505` 风控），而是数据量：
实测不带时间限制的全国查询约 **1358 万条**记录（单日 0.8 万 / 一周 17.5 万 / 一个月 62.7 万），
一次就是几十秒起。所以前端在选中「全国」的当下就把这条要求写在日期框旁边，缺日期时不发请求；
服务端再兜一道，避免别的入口漏检时把「全 0 的全国榜单」画出来当真实结果。

前端拿到 `needRange` 时的兜底文案在 `web/app.js` 的 `NATIONWIDE_NEED_RANGE`。

#### `/api/hot` 与本地的「正常 / 疑问」拆分

上游**没有**任何「正常记录数」字段 —— 榜单里的 `正常 N 条 · 疑问 M 条` 全是本地算的：

- 榜单主查询不带 `outside_type`（拿到该时段全部鸟种与总数）；
- 另发一次 `outside_type=1` 的查询，得到「疑问鸟种 → 疑问记录数」映射；
- 逐种相减：`正常 = count - doubtCount`。`/api/user-lifelist`（人生鸟种）也照这套口径给出三个数：
  `doubtSpeciesCount`（含疑问的种数）、`normalSpeciesCount`（`count - doubtCount > 0` 的种数）、
  `normalRecordSum`（正常记录条数合计）—— 它们是**交集计数**，不是简单相减：
  一个鸟种可能既有正常记录又有被标疑的记录，两边都算，所以 `normalSpeciesCount + doubtSpeciesCount ≠ 物种总数`。

### 3. 统计类（3 个）
| 上游接口 | 返回字段 | 本项目用途 |
| --- | --- | --- |
| `/front/record/taxon/num` | `taxon_num`、`taxon_order_num`、`taxon_family_num` | 概览卡「鸟种数」「目 / 科」 |
| `/front/record/activity/reportNum` | `report_num`、`open_report_num`、`privacy_report_num` | 概览卡「观鸟报告数」「公开报告」（`open + privacy = report_num`） |
| `/front/record/chart/summary` | `record_count`、`reports_count`、`taxon_count`、`report_num_1/2`、`record_num_1/2`、`taxon_num_1/2` | 概览卡「鸟种记录条数」 |

> 上游把每项计数拆成 `_1`（主口径）与 `_2`（子集，实测满足 `_1 + _2 = 总数`，对应「名录外记录」）两组，但站点未公开口径说明，因此本项目**只使用总量字段**，子集字段仅原样透出备用。

**这三个统计接口同样认 `pointname` / `username` / `taxonid`**（已实测），所以顶部「记录检索」的三个条件会让概览卡与榜单一起收窄，不会出现「卡片 152 种、榜单 71 种」这种对不上的情况：

| 条件（北京·全部时段） | `record/taxon/num` | `record/activity/reportNum` | `record/chart/summary` |
| --- | --- | --- | --- |
| 基准 | 1211 种 | 195,037 份 | 2,993,987 条 |
| `pointname=奥森` | 595 种 | 10,458 份 | 185,491 条 |
| `username=Zacco` | 130 种 | 44 份 | 685 条 |

### 4. 趋势类（2 个）

| 上游接口 | 返回 | 用途 |
| --- | --- | --- |
| `/front/record/search/TaxonCountBar` | `[{taxon_month, taxon_count, taxon_num_1, taxon_num_2}]` | 右侧「逐月鸟种数」柱状图 |
| `/front/record/search/ReportCountBar` | `[{taxon_month, report_num_1, reports_count, report_num_2}]` | 右侧「逐月报告数」柱状图 |

只返回**有数据的月份**，本项目会补齐成 1–12 月（缺的补 0）再画图。时间范围只有一天时，就只会有一个月的柱子——这是正常的。

### 5. 地区排行类（3 个）

| 上游接口 | 参数 | 用途 |
| --- | --- | --- |
| `/front/province/summary/chart` | `{year:'', version:'CH4'}` | 「全国各省鸟种数」排行 / 地图数据 |
| `/front/province/summary/chartCity` | `{names:'浙江省杭州市,浙江省宁波市', year:'', version:'CH4'}` | 「某省各地市鸟种数」 |
| `/front/province/summary/chartDistrict` | `{names:'杭州市西湖区,杭州市上城区', ...}` | 「某市各区县鸟种数」（本项目用 chartCity 实现，二者对区县名都可返回） |

返回 `[{name, value, report, record, total, version}]`，`value` 即鸟种数。

**这里有两个必须踩对的点：**
1. `names` 必须是「**上级行政区名 + 本级行政区名**」拼接——查浙江的地市要传 `浙江省杭州市`，查杭州的区县要传 `杭州市西湖区`。只传 `杭州市` 会返回空数组。
2. 必须带 `year`（可为空串）和 `version`，否则可能返回空；返回的是**裸数组**，且同一名称可能出现多条（不同版本），需要按名称去重取最大值。
3. 直辖市传 `北京市东城区` 这种形式即可，`chartCity` 同样能返回区县级数据。

### 6. 鸟种名录与保护等级（2 个）

| 上游接口 | 参数 | 用途 |
| --- | --- | --- |
| `/front/taxon/search` | `{name:'麻雀'}`；**不传参数返回全部 3098 条** | 「郑四名录」的全量来源（记录检索的鸟种名解析与 `/api/taxon-search` 都用它；页面底部原来的「按鸟种查看」面板已移除，接口保留）；后台预热保护等级时用它拿全量 id |
| `/front/taxon/level` | `{id: 4040}` | 每种鸟的保护等级 |

`/front/taxon/level` 返回：

```json
{ "taxon_id": 4001, "china_level": "国家二级", "iucn": "LC",
  "china_iucn": "LC", "cites": "", "is_china": "0" }
```

| 字段 | 含义 |
| --- | --- |
| `china_level` | 《国家重点保护野生动物名录》(2021)：`国家一级` / `国家二级` / `三有` |
| `iucn` | IUCN 红色名录全球等级：`CR/EN/VU/NT/LC/DD/NE/NR/EX/EW` |
| `china_iucn` | 《中国生物多样性红色名录》等级 |
| `is_china` | 是否中国特有（`"1"` / `"0"`） |
| `cites` | CITES 附录（当前未展示） |

**这是「保护等级」功能的唯一数据来源**，也是接口调用量最大的一处：榜单里每个物种都要查一次。因此做了三层优化（见下节）。

#### `/front/taxon/search` 的几个性质（做「按鸟种名称查询」时必须知道）

1. **只做中文名精确匹配**：`name=喜鹊` 能查到「喜鹊」，但**查不到**「灰喜鹊」；传学名（`Pycnonotus sinensis`）或英文名一律返回空。
2. **不传参数返回全部 3098 条**，返回顺序是按中文名的 hash 序（看不出规律）。
3. **每行都带一个 `version` 字段**（形如 `Z4-67FA07177A544FBD96006A7CC7489D25`）。实测全量 3098 行只有两个前缀：

   | version 前缀 | 行数 | 说明 |
   | --- | --- | --- |
   | `G3` | 1503 | 《中国观鸟年报-中国鸟类名录 3.0》 |
   | `Z4` | 1595 | **郑四**（《中国鸟类分类与分布名录》第四版） |
   | `CH4` | **0** | 站点下拉框里写的名字，在上游数据里并不存在 |

   `version` 参数**不被这个接口识别**（传 `version=CH4` 得到 `count=0`），只能用返回的字段自己筛。
4. **`record/activity/*` 认的 id 全在 `Z4` 那一族**：灰喜鹊 `4721`、喜鹊 `4734`、白头鹎 `4866`、丹顶鹤 `4236`、麻雀 `5383`。
   顺带一提，郑四名录里「喜鹊」只有 `4734`（`Pica serica`）一条，`G3` 族里那个 `700`（`Pica pica`）不在其中——
   所以**限定郑四名录后，同名歧义自然消失**。
5. 每行还带 `pinyin`（`huixique`）与 `szm`（首字母 `hxq`）两个字段，可直接用来做拼音检索。

本项目的 `/api/taxon-resolve` 就是**在郑四（`Z4`）名录里**解析名字的：

1. 服务端 `GET /api/taxon/search` 拉一次全量名录 → 按 `version` 前缀取 `Z4` 那 1595 条 → 缓存 **7 天**（进程内只回源一次）。
2. 用它建五个内存索引：中文名、学名、英文名、拼音、首字母。
3. 解析时逐级降级：**中文名精确 → 学名精确 → 英文名精确 → 拼音 → 首字母 → 中文名包含 → 学名/拼音包含**。
   所以 `灰喜鹊` / `Cyanopica cyanus` / `huixique` / `hxq` 都能解析到同一个 id。
4. 命中多条（例如用首字母模糊匹配）时把候选一并返回，前端列出让人选。

> 这么做有两个好处：**id 与榜单数据源同族，必然对得上**；而且整份名录长期缓存，
> 解析一次之后基本是纯内存查表，不需要为「认一个名字」再打一次上游。
>
> 早期的实现是「先读已缓存的地区鸟种清单」，缺点是要等页面先查过榜单才有池子可用；
> 换成郑四名录后，页面一打开就能解析。

### 8. 报告详情页的外链规则（已接入「点报告跳转」）

网页端点报告会跳到站点自己的详情页，URL 规则如下：

```
https://www.birdreport.cn/home/record/page.html?param=<Base64(JSON({reportId, ts}))>&sign=<MD5>
```

- `param` = `Base64(JSON.stringify({reportId, ts}))`，`ts` 是毫秒时间戳（页面并不校验它）
- `sign`：站点页面用 `calcMD5(parseParam)` 校验，`parseParam` 是解码后的**对象**。
  而站点 `md5.js` 的 `str2blks_MD5(str)` 直接读 `str.length` / `str.charCodeAt(i)`——
  传普通对象时 `length` 为 `undefined`（`NaN >> 6 === 0`）且循环不执行，等价于对空串求 MD5。
  所以 **`sign` 恒为 `md5('')` = `d41d8cd98f00b204e9800998ecf8427e`，与 reportId 无关**（已用站点自己的 md5.js 实测确认）。
- 校验不通过时页面会把 `reportId` 置 0、不加载任何报告，所以 `sign` 必须原样带上。
- 实测结论：该链接**无需登录**即可打开报告详情（观鸟点、时段、记录人、鸟种清单齐全）。

服务端在 `/api/records` 的每条记录上直接给出拼好的 `url` 字段，前端不需要关心这套规则。

### 9. 按用户名查报告（`searchUserRecords`）—— 与地区、时间无关的一条路

「我的」面板里的**我的报告**要的是「这个人在记录中心公开过的全部报告」，与页面上选的地区 / 日期无关，
所以它走的是 `/api/records` 的另一条分支：**只给 `username`、不给 `province`**。

这里有三处与地区查询不同，都是实测出来的：

- **`username` 必须带 `mode=1`（精确）**。不带的话会把名字里含同一子串的**别人的**报告也算进来
  （`kkia` 模糊 229 种 / 精确 212 种，多出来的 17 种来自别的用户名）。
- **必须带 `version=CH4`**，与「人生鸟种」同口径（郑四分类），否则同名两个名录版本的 id 会对不上。
- **`outside_type` 传空串而不是 `0`**。官方站点默认发 `0`（只看正常），那会**静悄悄少掉**带疑问记录的报告；
  传 `''` 才是全部。每一行里的 `outside_count` 再告诉我们这份报告有几条记录被标疑，用来把观鸟点标红。

早期有一条错误的结论是「记录明细必须带 `province`」——那是把一次 `505` 风控误读成了缺参数，已纠正：
**不带地区、只带用户名的查询是合法的**，返回该用户**全部公开报告**（分页）。

## 三、上游接口 → 本地 REST 的对应关系

页面不直接调上游，全部经过本地服务端（这样才能加密、缓存、聚合、限流）：

| 本地接口 | 用到的上游接口 |
| --- | --- |
| `GET /api/provinces` | `adcode/province` |
| `GET /api/cities` | `adcode/city` |
| `GET /api/districts` | `adcode/district` |
| `GET /api/overview` | `record/taxon/num` + `record/activity/reportNum` + `record/chart/summary`（**并行 3 个**） |
| `GET /api/hot` | `record/activity/taxon` + `taxon/level`（批量补全保护等级）。榜单按 `recordcount` 升序输出，缓存 24 小时 |
| `GET /api/taxons` | `record/activity/taxon`（与 `/api/hot` **共用同一份缓存**，不重复回源） |
| `GET /api/records` | `record/activity/search`（**只取上游一页**，默认每页 10 条、上限 50；支持 `page` / `limit`） |
| `GET /api/trend` | `record/search/TaxonCountBar` + `record/search/ReportCountBar`（并行） |
| `GET /api/province-rank` | `province/summary/chart` |
| `GET /api/region-rank` | `adcode/province`(→code) + `adcode/city` + `adcode/district` + `province/summary/chartCity` |
| `GET /api/taxon-search` | `taxon/search`（全量名录，限 `version` 前缀 `Z4` = 郑四）+ `taxon/level` |
| `GET /api/taxon-resolve` | 同上（同一份 7 天名录缓存），纯内存匹配，不再额外回源 |
| `GET /api/taxon-level` | `taxon/level` |
| `POST /api/protection/sync` | `taxon/search`（全量 id）+ 逐个 `taxon/level` |
| `GET /api/watch` · `POST /api/watch` · `GET /api/watch/check` · `POST /api/watch/history` | **不直连上游**：复用 `/api/hot`（强制 `nocache=1`）+ 同一份近两年历史缓存，见下面「监听在服务端怎么实现」 |

**控制上游压力的三道闸门：**

1. **并发合并**：同一个 key 的并发请求只跑一次上游调用。
2. **结果缓存**：榜单缓存 **24 小时**（一天失效一次），概览 / 趋势 / 地区排行缓存 10 分钟，郑四名录缓存 7 天；全部落盘，重启读入内存继续用；切筛选 / 排序 / 翻页不再回源。
3. **等级字典**：`taxon/level` 按鸟种 id 长期持久化，只补缺失项；并发 4、每次间隔 60ms。首个地区补全后，其它地区直接复用，全国 3098 种只需拉一轮。

例：查询「杭州市西湖区 · 当天」实际产生的上游调用只有 **4 次**（榜单 + 统计 ×3），趋势 2 次、地区排行 1 次；保护等级则几乎全部命中本地字典。

#### 监听（`/api/watch`）在服务端怎么实现

监听器（`server/watch.mjs`）本身**不新增任何上游调用路径**：它按存下来的条件调 `loadHot(conditions, { nocache: true })`，
也就是走一遍 `/api/hot`（本时段清单 + 近两年历史 + 疑问标记），再按阈值筛。几个必须知道的点：

1. **必须强制回源**。榜单的本时段清单缓存 24 小时（`HOT_TTL_MS`），照抄缓存的话「每 10 分钟检查一次」
   一天都是同一份数据、永远查不出新鸟。所以每轮检查都带 `nocache=1`。
2. **但又不能真的每 10 分钟打一次上游**。所以另设一道**最短回源间隔** `minFetchGapMs`（默认 **30 分钟**）：
   没到点的轮次直接复用上一轮结果（返回 `skipped: true` 与 `nextFetchInMs`），根本不碰上游。
   前端按 10 分钟轮询 → 实际回源 30 分钟一次，一天 48 次。
3. **历史口径取不到就整轮跳过**。若 `hot.stat.historyUsed === false`（上游风控 / 范围过大导致退回「按本时段记录数排序」），
   此时各行的 `historyCount` 不可信，按阈值筛会筛出空、看着像「没有稀有鸟」。
   所以这一轮直接跳过并如实写进 `lastError`，前端会把它显示出来。

`POST /api/watch` 的三种语义（默认**开着**、条件自动跟随）：

| 请求 | 含义 |
| --- | --- |
| `?enabled=1&…` | 打开监听；开着时再调 = 按新条件 / 新数量重来一遍（重建基线） |
| `?enabled=0` | 关闭监听（条件留着，`everConfigured` 记成 true —— 页面之后不会再自动打开） |
| **不给 `enabled`** | **只同步条件、不动开关**：页面每次查询成功后自动跟随条件走的就是这条。条件与数量都没变时**直接返回、不回源**（一次本地请求，不打上游）；变了就重建基线。页面用 `defer=1`，不等基线跑完就返回（建基线要真回一次上游、几十秒，不能让页面干等） |

状态存 `data/watch.json`（`runtime.mjs` 决定的缓存目录，源码形态下就是仓库的 `data/`）：
`{ enabled, everConfigured, conditions, label, maxHistoryCount, intervalMs, minFetchGapMs, baseline, baselinePending, alerted, history, lastCheckAt, … }`。

- **默认开着（`enabled: true`）**：全新安装时状态里还没有 `conditions`，服务端什么也做不了；
  页面一打开就 `GET /api/watch` 看到 `everConfigured === false`，于是把当前条件同步过去、自动开起来，
  并弹一句「已默认开启稀有监听（可在「我的」里关掉）」。
  `everConfigured` 是「用户是否亲手配过」的记号：`false` 才自动开，`true` 之后完全尊重用户的开关。
  旧版本的状态文件没有这个字段，用「有没有 `conditions`」迁移判断（旧版的「关闭」不清条件）。
- **基线（`baseline`）**：开启监听（以及**改条件 / 改数量**）的那一刻，把当下命中的鸟种 id 记成基线，
  这些**不产生提醒** —— 否则一开启就刷出几十条「新发现」。重建基线时 `alerted` 与 `history` **不动**：
  换个区县不该把已经报过的鸟再报一遍，历史记录也是日志不是缓存。
- **`baselinePending`**：从「基线已清空」到「那一轮真正查完」之间的空档。这期间基线是空的，
  普通检查若放行，会把当前命中的**一整批**鸟误报成「新发现」—— 所以 `check` 见到它就跳过提醒，
  **并就地把它当成「建基线」那一轮跑**（否则上游一抽风就永远建不出基线、监听永远不提醒）。
  基线那一轮没成功（上游取不到 / 历史口径缺失）时 `baselinePending` 保持 true，下一轮轮询继续补。
- **已提醒（`alerted`）**：每个报过的 id 只报一次；重启不会重报（id 存在状态文件里）。
- **历史（`history`）**：提醒日志，倒序，最多 500 条。**关闭监听 / 重开都不清空它**，
  只有 `POST /api/watch/history` 会清（且清历史不影响 `alerted`，所以清完不会把旧鸟再报一遍）。

前端拿到的快照字段：`enabled / everConfigured / conditions / label / maxHistoryCount / intervalMs / minFetchGapMs /
baselineCount / baselinePending / alertedCount / history / lastCheckAt / lastCheckOk / lastError / scanned / rareCount / minHistoryCount`。
`check` 的返回还会多一个 `newAlerts`（每条含 `ts / taxonId / name / latin / count / historyCount / chinaLevel / …`，
以及**当时盯的条件**，历史记录里要能看出来）。

### 版本与更新（`/api/version`、`/api/update/*`）

**不碰观鸟记录中心**，只查 GitHub Releases（`server/update.mjs`）：

```
GET  /api/version[?force=1]    当前版本 + 最新版本（默认走 6 小时缓存）
POST /api/update/download      开始下载本平台对应的产物（立刻返回）
GET  /api/update/progress      下载进度 {state, received, total, path, dir, error}
POST /api/update/reveal        在文件管理器里打开下载目录（桌面形态）
POST /api/update/open          用系统浏览器打开 Release 页面
```

**当前版本从哪来**（`server/version.mjs`，四个来源按优先级取第一个）：

| 优先级 | 来源 | 用在哪 |
| --- | --- | --- |
| 1 | `BIRD_VERSION` 环境变量 | CI 打 tag 时给的就是 tag |
| 2 | `web/version.json` | **打包脚本写进去**的：exe 的内嵌资源、APK 的 assets 都从 `web/` 整目录来，所以发出去的包知道自己是什么版本 |
| 3 | `git describe --tags --abbrev=0 --match 'v*'` | 源码方式跑（开发机上自动跟着 tag 走，不用手改文件） |
| 4 | `'dev'` | 都没有（**不参与版本比较**，见下） |

**「有没有新版」的判定**：把最新 tag 与当前版本按数字段比（`isNewer`）。任何一边解析不出数字段
（比如源码运行时的 `dev`）→ 一律 `hasUpdate: false` —— **不知道就别说有更新**，免得挂个撤不掉的红点。

**平台与产物**（命名规则见 `.github/workflows/release.yml`）：
`process.platform` 在 Android 上不一定可靠，所以原生壳在 `native-lib.cpp` 里显式设了
`BIRD_PLATFORM=android-arm64`。挑产物先按平台标识精确匹配（`…-win-x64.zip` / `…-android-arm64.apk`），
没匹配上再退一步：Android 拿任意 apk，桌面拿同系统的 zip（例如 mac-arm64 没出包时先给 Intel 包走 Rosetta）。

**下载**由**服务端**做（网页跑在 WebView 里写不了磁盘、也调不起安装器）：流式写进
`data/download/v<版本>/`，网页每 500ms 轮询 `/api/update/progress` 画进度条。下完的收尾分两种形态：

- **Android** —— 网页经 JS 桥调 `BirdAndroid.installApk(绝对路径)`，壳把它换算成
  `content://com.birdreport.hot.files/…`（自写的 `ApkFileProvider`，不引 AndroidX）交给系统安装器；
  清单里需要 `REQUEST_INSTALL_PACKAGES`，API 26+ 还要用户允许「安装未知应用」（系统会自己引导）。
- **Windows / macOS** —— 自动解压 zip（PowerShell `Expand-Archive` / `unzip` / `tar`），
  并打开文件夹让用户替换（运行中的 exe 锁着自己那个文件，无法自我覆盖）。

**可用的环境变量**（都有默认值，正常跑不用管）：

| 变量 | 作用 |
| --- | --- |
| `BIRD_VERSION` | 覆盖当前版本号（打包 / 调试用） |
| `BIRD_PLATFORM` | 覆盖平台标识（Android 壳会设） |
| `BIRD_UPDATE_REPO` | 查哪个仓库，默认 `hjfdb/birdreport-rare-birds` |
| `BIRD_UPDATE_API` | API 根地址，默认 `https://api.github.com`（GitHub Enterprise / 镜像 / 测试桩） |
| `BIRD_UPDATE_TTL_MS` | 检查结果缓存时长，默认 6 小时 |
| `BIRD_NO_OPEN_FOLDER` | `1` = 不真的打开文件夹 / 浏览器（无 GUI 环境、自动化测试用） |

> ⚠ GitHub 未登录的 API 限额是**每 IP 每小时 60 次**，所以「我的」面板一打开就查的那次默认走
> 6 小时缓存，只有点「检查更新」才 `force=1`。检查失败**不算检查过**：保留上一次结果与
> `checkedAt`，只把 `error` 报出去，界面据此显示「上次检查是几点、这次没连上」。

### 风控（务必注意）

请求过于频繁时，上游会返回：

```json
{ "code": 505, "count": 0, "success": false }
```

站点前端拿到 `505` / `405` 就弹验证码（`record-page.html` 里的 `BIRDREPORT_VISIT.codeHtml()`）。

**这类响应必须抛错，绝不能当成「空结果」缓存**——否则页面会在整个 TTL 内一直显示 0。
`server/birdreport.mjs` 的 `api()` 里对此做了拦截（`success === false && data === undefined` → 抛错），
并且标记 `noRetry` 立即失败：**风控重试只会更糟**，而 `code 500`（范围过大）往往要 20 秒才吐出来，
按原策略重试 3 次会把一次失败拖成一分钟的等待。`server/index.mjs` 里容忍子接口失败的 `soft()` 也会让风控错误冒泡。
遇到时等几分钟再试即可。
